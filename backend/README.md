# CashGuard — выявление нарушений кассовой дисциплины по видео

Сервис принимает видеозапись кассы, находит визуально наблюдаемые признаки возможных нарушений и возвращает таймкод, кадры-доказательства, описание и ссылку на пункт нормативного акта РК. Все модели работают локально, без облачных AI-сервисов.

## Архитектура

```
видео ─► ffmpeg: кадры 2 fps, 336 px ─► окна по 8 с (шаг 6 с)
      ─► VLM (Qwen3.5-9B, llama.cpp): по каждому правилу вопрос «да/нет»
         вероятность берётся из logprobs ответа, а не из текста
      ─► оценка правила = его вероятность минус средняя по всем правилам в этом окне
      ─► для правил выше порога: вопрос «в каком кадре» (буква кадра, тоже по logprobs)
      ─► детектор RT-DETRv2 на тех же кадрах: люди и ноутбук → зона стола,
         моменты ухода и промежутки, когда у стола никого нет
      ─► D-03, A-04 засчитываются только около ухода, таймкод = момент ухода
      ─► A-01 = стол пуст + «на экране рабочее окно» по увеличенному фрагменту экрана
      ─► OWLv2 (поиск по тексту) находит сейф; фрагмент сейфа каждые 3 с:
         D-02 = дверца открыта на 3 фрагментах подряд (≈ 6–9 с), а не мельком
      ─► слияние событий, пороги по правилам (rules/thresholds.json)
      ─► короткое описание видимых действий + кадры t, t±1 с
      ─► пункт нормы из каталога rules/catalog.json (модель ссылки не пишет)
```

Ключевые решения:
- **Вероятности вместо самооценки.** Модель отвечает одним токеном `yes/no`, уверенность — `p(yes) / (p(yes)+p(no))` из logprobs. Самооценка модели в тексте («уверенность 0.95») оказалась некалиброванной.
- **Поправка на уклон окна.** На «насыщенных» окнах Qwen3.5-9B отвечает «да» почти на все правила сразу. Вычитание средней вероятности окна оставляет только то, что выделяется на фоне остальных правил (`SCORE_NORM=window`, по умолчанию; `none` — сырые вероятности). На 40 роликах это подняло точность leave-one-out с 0.675 до 0.725 и совпадение типа с 5/16 до 8/17.
- **Детектор вместо «кассира нет» от модели.** Момент ухода и пустой стол даёт RT-DETRv2 по каждому кадру; зона стола строится по найденному ноутбуку, без ручной разметки ракурса. Если ноутбук не найден, правила ухода не фильтруются, а A-01 не проверяется.
- **Фрагмент экрана для A-01.** На целом кадре экран ноутбука занимает 1–2 токена изображения, на увеличенном фрагменте — сотни: 9B уверенно отличает рабочее окно от экрана блокировки (0.96 против 0.04 на паре X-28/X-29). Вместе с детектором это подняло leave-one-out до 0.800 (18 из 21 найдено, 5 ложных из 19).
- **Сейф по фрагменту для D-02.** Сейфа нет среди классов RT-DETRv2, поэтому его находит OWLv2 по тексту «a metal cabinet» на 5 кадрах; берётся рамка, которая стоит на одном месте во всех кадрах (человек за стеклом двигается, сейф — нет). Открытый мельком сейф (кладут или берут) не считается: нужна открытая дверца на 3 фрагментах подряд. Leave-one-out вырос до 0.825.
- **Запас порога 0.02.** Порог стоит на 0.02 выше максимума чистых роликов (`calibrate.py --margin 0.02`). Повторный прогон llama.cpp сдвигает оценку окна в среднем на 0.015, в 10% окон больше чем на 0.038, максимум 0.14, так что запас покрывает не всё (см. «Результаты и известные ошибки»).
- **Ссылки только из каталога.** Модель выбирает правило, а документ, пункт и требование подставляются из `rules/catalog.json`. Выдуманных ссылок быть не может.
- **Пороги по правилам** подбираются по роликам без нарушений (`eval/calibrate.py`): порог правила — чуть выше максимума его оценки на «чистых» видео. Это прямо ограничивает ложные срабатывания.
- **Дедлайн 270 с** от момента загрузки: если не успеваем, возвращаем найденное по просмотренной части, а не таймаут.
- **Без распознавания лиц.** Модель видит людей только как «кассир», «клиент», «посторонний».

## Запуск локально (macOS, Apple Silicon)

```bash
llama-server -m Qwen3.5-9B-Q4_K_M.gguf --mmproj mmproj-Qwen3.5-9B-BF16.gguf \
  --port 8081 -c 32768 -np 2 --image-max-tokens 256 --reasoning off
uv venv --python 3.11 && uv pip install -r pyproject.toml
DETECTOR=off API_KEY=<ключ> .venv/bin/uvicorn app.main:app --port 8000
```

Без torch детектор выключается через `DETECTOR=off`; с ним — `uv pip install -r pyproject.toml --extra detector`. Пороги в `rules/thresholds.json` подобраны для режима с детектором.

API: `http://localhost:8000/api/v1`. Интерфейс запускается отдельно из `app/`.

## Запуск на GPU-сервере

Веса (`Qwen3.5-9B-Q4_K_M.gguf`, `mmproj-Qwen3.5-9B-BF16.gguf`) положить в `./models`, затем:

```bash
API_KEY=<ключ> docker compose up -d --build
```

После загрузки весов интернет для обработки видео не нужен: веса детекторов скачиваются при сборке образа, в работе стоит `HF_HUB_OFFLINE=1`.

Без Docker (как на L4): `deploy/gpu_setup.sh` ставит llama.cpp, веса и Python-окружение, `START_APP=0 deploy/gpu_start.sh` поднимает llama-server, `API_KEY=<ключ> deploy/install_service.sh` ставит API как systemd-сервис `cashguard` с автоперезапуском (ключ хранится в `.env` с правами 600).

`deploy/gpu_start.sh` запускает llama-server с `--cache-ram 1024`: по умолчанию кэш промптов в оперативной памяти растёт до 8 ГБ и вместе с контрольными точками гибридной модели заполняет 16 ГБ машины.

## API

Все запросы с заголовком `X-API-Key`.

```bash
curl -X POST https://<host>/api/v1/analyze -H "X-API-Key: <ключ>" -F "file=@video.mov"
curl https://<host>/api/v1/jobs/<job_id> -H "X-API-Key: <ключ>"
```

Контракты фронтенда (`app/src/lib/api/contracts.ts`, `jury-contracts.ts`,
`health-contracts.ts`) определяют HTTP-пейлоуды. `ANALYSIS_API_URL` фронтенда
должен указывать на `https://<host>/api/v1`.

- `POST /api/v1/analyze`: один MOV до 100 MiB; `202 {"job_id":"..."}` после
  проверки видеопотока и сохранения задачи. Ошибки имеют форму
  `{"error":{"code":"...","message":"..."}}`; нечитаемое видео — 422.
- `GET /api/v1/jobs/{job_id}`: представление для жюри, кадры JPEG в base64.
- `GET /api/v1/jobs/{job_id}?view=ui`: прогресс по этапам во всех состояниях;
  после завершения — `overview`, `verdict`, `violations_count` без изображений.
- `GET /api/v1/jobs/{job_id}/violations?page=1&page_size=20`: неизменяемые
  события в порядке `(timecode_sec, id)`, нормативные источники и ссылки на кадры.
- `GET /api/v1/jobs/{job_id}/violations/{violation_id}/frames/{frame_id}`:
  JPEG-байты с авторизацией тем же ключом.
- `GET /api/v1/health`: авторизованная проверка бэкенда и сервиса модели;
  200 при доступности обоих, 503 при недоступности модели.

Все ответы запрещают кэширование. Устаревшие `/ui/*` и `/health` удалены.
Обзор генерирует локальная LLM из результата анализа; ошибка генерации завершает
задачу с `OVERVIEW_GENERATION_FAILED`. Общий лимит включает очередь и обзор.
Задачи, прерванные перезапуском сервиса, возвращают `ANALYSIS_FAILED`.

Проверка реальных ответов FastAPI исходными Zod-схемами фронта (без GPU):

```bash
cd app
BACKEND_PYTHON=/path/to/backend/.venv/bin/python npm run contracts:test:backend
npm test
npm run contracts:check
```

Python-окружение должно содержать зависимости из `backend/pyproject.toml`, а
фронтенд — установленные npm-зависимости. Тесты подменяют инференс, но используют
настоящие HTTP-маршруты, сохранение результата и JPEG-файлы.

Проверка развёрнутого сервиса по контракту (ключ, коды ошибок, строгая схема, JPEG-кадры, лимит 5 минут):

```bash
API_KEY=<ключ> .venv/bin/python eval/check_api.py --base https://<host> video1.mov video2.mov
```

Время обработки: одно видео до 145 с — около 200 с на L4; пять типичных роликов датасета одновременно — 150–180 с. Каждая задача получает не больше окон в очереди к модели, чем у неё слотов, поэтому одновременные задачи идут вперемешку. Если к дедлайну (270 с) не успеваем, пропускаются окна через одно по всему видео, а не конец ролика; жёсткий предел задачи — 295 с, после него `failed`.

## Оценка качества

```bash
.venv/bin/python eval/run_eval.py --out runs/eval/catalog   # оценки по окнам, кэш по роликам
.venv/bin/python eval/run_detector.py --frames-from runs/eval/catalog
.venv/bin/python eval/run_facts.py --out runs/eval/facts_v2
.venv/bin/python eval/calibrate.py --run runs/eval/catalog --detect runs/eval/detect \
  --facts runs/eval/facts_v2 --margin 0.02 --write rules/thresholds.json
```

`calibrate.py` печатает качество in-sample и leave-one-out (каждый ролик оценивается порогами, подобранными без него); с `--groups eval/setups.json` — leave-one-setup-out.

Прогон всех роликов через работающий сервис и подсчёт по сохранённым ответам:

```bash
API_KEY=<ключ> .venv/bin/python eval/run_service.py --base http://127.0.0.1:8000 --out runs/eval/service
.venv/bin/python eval/run_service.py --score runs/eval/service
```

Видео отправляются через `/api/v1/analyze`, результат читается из авторизованного `/api/v1/jobs/{job_id}`. Тип связывается с каталогом локально. Для новых прогонов `run_service.py` выбирает первое событие по времени; прежний выбор по внутреннему confidence удалён из публичного контракта. Историческая таблица ниже использовала прежний выбор события и не является результатом новых прогонов.

## Нормативные источники

- Правила осуществления кассовых операций и операций по инкассации банкнот, монет и ценностей, утв. постановлением Правления НБРК от 29.11.2019 № 231 — https://adilet.zan.kz/rus/docs/V1900019680
- Правила организации охраны и устройства помещений банков второго уровня, утв. постановлением Правления НБРК от 24.02.2020 № 14 — https://adilet.zan.kz/rus/docs/V2000020075
- Требования к обеспечению информационной безопасности банков, утв. постановлением Правления АРРФР от 03.04.2026 № 53 — https://adilet.zan.kz/rus/docs/V2600038336

Все пункты сверены с текстом действующих редакций на adilet.zan.kz 17.10.2026. Пункт 16 Правил № 14 до 01.01.2027 действует во временной редакции (постановление НБРК от 24.12.2024 № 88), подп. 1) в ней совпадает.

## Как правило связывается с видео

Каждое правило в `rules/catalog.json` — это связка «видимый признак → норма»:

- `visual` — что именно должно быть видно в кадрах (на английском, это текст вопроса модели);
- `not_violation` — похожие ситуации, которые нарушением не считаются;
- `source`, `clause`, `requirement` — документ, пункт и требование, сверенные с текстом на adilet.zan.kz;
- `interpretation` — норма прямо не описывает действие и применена по смыслу.

Модель только отвечает «да/нет», виден ли признак в окне или на фрагменте. Тип нарушения, документ, пункт и требование подставляет код из каталога, поэтому ссылку модель придумать не может. В ответе `description` = что видно на видео + «Основание: <документ>, <пункт>: <требование>.» Правила, для которых нужны невидимые данные (проводки, сверки, подлинность купюр), в каталог не включены.

## Результаты и известные ошибки

40 уникальных роликов датасета (21 с нарушением, 19 без), Qwen3.5-9B на L4.

| Проверка | Вердикт верен | Найдено | Ложных | Тип верен (из найденных) | Тип и таймкод ±2 с верны |
|---|---|---|---|---|---|
| leave-one-out (пороги без проверяемого ролика) | 0.825 | 18/21 | 4/19 | 11/18 | 5/21 |
| leave-one-setup-out (13 ракурсов камеры, ракурс откладывается целиком) | 0.825 | 18/21 | 4/19 | 11/18 | 5/21 |
| свежий прогон через API, текущие пороги | 0.825 | 17/21 | 3/19 | 11/17 | 5/21 |
| то же на зеркально отражённых роликах | 0.750 | 17/21 | 6/19 | 11/17 | не пересчитано |

«Вердикт верен» и «Найдено» — только ответ «есть нарушение / нет». «Тип и таймкод ±2 с верны» — главное нарушение в ответе совпало с разметкой по типу и по времени; знаменатель — все 21 видео с нарушением. Полностью верно сейчас 5 видео из 21: X-11, X-20, X-26, X-30, X-46. В шести найденных видео (X-1, X-4, X-13, X-17, X-22, X-34) вердикт верный, а тип нет.

Строки leave-one-out считает `calibrate.py` (строка `type and time within 2 s`) по сохранённым оценкам окон, детектора и фрагментов (`runs/eval/catalog`, `runs/eval/detect`, `runs/eval/facts_v2`), строки прогона через API — `run_service.py --score` (`type_and_time2s`) по сохранённым ответам сервиса. Эти данные пока лежат только на сервере и в репозиторий не добавлены, поэтому таблицу со стороны не проверить; добавим их вместе с повторным прогоном.

Известные ошибки:
- Не находятся: X-2 (приём денег без удостоверения, B-02), X-32 (дверь не закрыта, D-13), X-44 (отбракованная купюра, D-18); X-24 (документы на столе, A-04) — на грани порога.
- Ложные на грани порога: X-12 (еда), X-25 (наличные без присмотра), X-27 (посторонний; вероятно, отражение в стекле).
- Группа пересчёта денег (D-04, D-05, D-06, D-18) по типу не определяется: вместо неё модель называет D-01 «наличные без присмотра».
- D-02: если кассир сама открывает сейф сидя рядом, на отражённом ролике это может засчитаться как «сейф открыт» (X-8, X-39).

## Ограничения

- Модель видит кадры с частотой 2 fps; очень быстрые действия рук могут быть пропущены.
- Не проверяется то, что не видно на видео: проводки, сверки, содержимое документов. Нарушения «по бездействию» (не проверил удостоверение, не пересчитал) по редким кадрам определяются ненадёжно.
- Таймкод — момент, когда признак впервые хорошо виден, а не начало действия.
- Распознаются только 18 типов из каталога; новые типы из теста (FAQ 9) не найдутся.
- Повторный прогон того же видео может поменять вердикт пограничного ролика: на 40 роликах так меняется около 4.
- Чувствительность к ракурсу: на зеркально отражённых роликах точность 0.750 против 0.825, детекторы ноутбука и сейфа при этом находят объекты так же.
- Мощность одной L4: пять самых длинных роликов датасета сразу (410 с видео) не успевают целиком — часть окон пропускается, а составные проверки A-01/D-02 отключаются. Пять типичных роликов сразу обрабатываются за 150–180 с.
- Без распознавания лиц: роли людей определяются по положению и действиям, а не по личности.
